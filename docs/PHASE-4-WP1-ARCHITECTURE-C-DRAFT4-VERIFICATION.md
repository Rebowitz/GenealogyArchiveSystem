## 3. V1: what is corrected, and the actual exclusion theorem

The following are satisfactory architectural corrections:

- Contract §5.4: application_name is diagnostic/candidate/refusal information only. Neither a negative census nor a positive label authorizes reclaim or termination. No census is part of T-6.
- T-1/T-4/T-6 remain short outermost ownership transactions. Acquisition commits before effects; release follows quiescence, storage outcomes and known EDT outcomes. Unknown acquire/release/reclaim outcomes use the independently recorded own attempted backend tuple and T-2; the runtime sends no signal.
- §10.4 restricts targeted administrative termination to independently recorded attempted-backend tuples, revalidated and followed by confirmed absence. Otherwise the existing producer exclusion/admission closure/offline drain supplies the conservative fallback. §10.1 correctly distinguishes the runtime program prohibition from PostgreSQL's default same-role signalling permission; no broad runtime signalling grant is needed.
- T-3 now explicitly places token-owned O before ordered locks, including all participating O rows in UUID order for multi-operation EDTs. The advisory-owned premise is expressly replaced. A mismatch rolls back the whole window; helper I/O threads issue no EDTs.

**Conditional proof:** suppose every EDT obtains its subject's qualifying O lock before effects-dependent writes or other conflicting row/key acquisitions, retains it until transaction end, checks the exact interval and aborts on mismatch. A still-running old EDT that already holds that authority prevents the reclaim's conflicting lock. If reclaim wins first and changes the interval, an old predicate cannot subsequently confer commit authority. E-1 prevents new work by the old process; P3 separately governs already accepted storage requests. This proves subject-specific stale-commit exclusion. It does not prove that the backend ended, holds no compatible lock, or can cause only harmless waits across every other path.

T-3's mismatch must be tested with fresh reads and actual PostgreSQL transactions; cached pre-reclaim domain objects are not a substitute for re-reading recovery state after reclaim. An old backend whose client died need not actively execute a Java rollback: it may remain until PostgreSQL ends the session. Safety must rely on failure to obtain qualifying authority and absence of authorized later mutations, not prompt socket detection.

The SQL form SELECT … FOR NO KEY UPDATE NOWAIT followed by CAS/event is executable. The predicate-recheck argument uses READ COMMITTED, as retained windows specify; stronger-isolation serialization failures must roll back and refuse/retry, never count as acquired authority. NOWAIT covers row locks, while table-lock waiting needs the separate bound. lock_timeout applies to individual explicit and implicit lock waits, not a universal elapsed-time bound for the whole transaction. Every timeout rolls back the attempt and proves no attribution. [SELECT documentation](https://www.postgresql.org/docs/16/sql-select.html), [lock_timeout documentation](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-LOCK-TIMEOUT).

## 6. New findings and exact corrections

### D4-V1 — MAJOR: the renewal exception does not exclude the new multi-O cycle

**Contract evidence:** T-3 lines 360–361; §5.4.1 lines 472–480 claims renewal's RECEIVING rows are taken by no other multi-row locker. §5.8 line 590 makes destruction's subjects DESTROY plus every other writer's token. The response explicitly leaves renewal and destruction to the future inventory while asserting the theorem.

**Source evidence:** RepairService:37–55 creates REPAIR/RECEIVING rows with persisted content X and calls the shared IngestionService.stage. IngestionService:46–80 maintains one receiving set and renews it in a single timer call. FileOperationRepository:289–296 uses UPDATE … ANY(:ids), without an acquisition order or interval predicate. DestructionProcessor.otherWriters:111–130 includes these non-final operations. Its STOPPABLE set (:36–37) excludes RECEIVING, so cancellation does not by itself remove that overlap. The retained proposal's A2 already admits renewal uses scan order; UUID-sorting the input array supplies no physical ordering guarantee.

**Plausible schedule under the proposed extension:**

1. Two receiving REPAIR operations A and B of X belong to one JVM, A < B by UUID. That JVM sends a multi-row renewal statement, then dies. Its advisory session is gone, but the renewal backend remains before it has locked either row. This is precisely the surviving-backend fault model the draft supports.
2. Destruction/recovery establishes E-1 and, while both rows are free, reclaims both intervals in separate successful T-6 transactions. The still-RECEIVING rows retain the renewal predicate. No existing row holder made these reclaims fail.
3. The old renewal backend resumes and updates B first (a permitted scan order), retaining B while it proceeds toward A. It does not check effect_interval_id; renewal is expressly token-free.
4. The replacement's multi-operation EDT locks A first, then requests B. The renewal requests A. The graph is **replacement holds A → waits B; renewal holds B → waits A**.

This is a counterexample to the claim that every competing O waiter holds nothing, not an assertion that such a Draft 4 implementation exists or that 40P01 was observed. It requires the proposed multi-operation prefix to include these receiving operations; the current contract does not exclude them and its destruction subject rule points the other way. A live original JVM would prevent reclaim; the schedule deliberately uses a surviving server statement after verified JVM death. Per-JVM disjoint renewal sets do not exclude it. E-2 fences EDT authority, not token-free renewal statements. A timeout may break a wait, but it does not establish deadlock freedom.

**Smallest correction:** make renewal **one operation per outermost committed transaction**, without an enclosing batch transaction. Alternatively explicitly lock all renewed rows by deterministic per-ID acquisition in the same UUID order as every multi-O EDT, then renew; do not rely on ANY-array order. Preserve independent lease renewal and stale/progress predicates. A narrower exclusion of RECEIVING rows from every multi-O path is defensible only with an explicit source-derived set/transition proof covering destruction, reclaim and cleanup; it is not supplied now. The single-row alternative avoids that new exclusion argument and adds no durable machinery.

Amend the class table and no-cycle proof accordingly. Require a deterministic real-PostgreSQL test with the old renewal backend surviving its process and the replacement overlapping the operation set. Observe named backend barriers/blockers, disable retries, assert zero SQLSTATE 40P01 on the corrected path, and distinguish expected refusal/timeout from success. Preserve the actively renewing slow-upload regression. No test is run by this report.

**Timing:** contract correction before owner acceptance; actual inventory/reordering and tests before implementation acceptance. No new owner policy or framework is needed.

### D4-N1 — MINOR: align traces and proof wording with the fence actually proved

- **T-a, line 508**, still shows “Ct, Q, then token-owned O”. That directly contradicts T-3's mandatory O prefix. Change the example to O → Ct → Q.
- **T-6 argument step 2, line 423**, says any holder of O makes NOWAIT fail. KEY SHARE is compatible with NO KEY UPDATE; scope this statement to conflicting locks/EDT authority.
- **Steps 3–4 and §5.4.1** should say a stale interval cannot obtain a **qualifying predicate/commit authority**, rather than claiming the backend can never physically lock the row. PostgreSQL can lock a row that matched the original snapshot even when an updated version no longer qualifies; an old mismatch may leave only a harmless lock until transaction end. For multi-O EDTs, a stale backend can also already hold a lower-UUID prefix, so “holds no lock of that window” needs that qualification. Such a prefix is safe only because it takes no later business locks after mismatch and the competing prefix has a common order.

These wording corrections do not invalidate the conditional stale-commit fence, and require no stronger O lock. [PostgreSQL row-lock compatibility](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS), [SELECT locking-clause semantics](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE), [READ COMMITTED rechecking](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED).

## 8. Necessity, convergence and next gate

The token remains justified by lost-advisory/live-I/O cases. Ct and claim coordination remain justified by cross-operation publications and accountability. The offline fence/freeze/drain addresses installation-wide and legacy authority. A single advisory lock cannot replace those different boundaries. Removing label authority is a material simplification, and the V4, migration and cancellation corrections demonstrate convergence.

**Required trend assessment:** the last review exposed the label-authority structural gap; this review exposes a new interaction between the O prefix and multi-row renewal. Two consecutive reviews therefore require this recorded system-wide complexity assessment. No new persistent state or framework is necessary: the simpler alternative is single-row renewal transactions and a corrected finite wait-set argument. There has been demonstrated convergence (V2/V3 remain corrected, V4 now closes, label authority is removed), so the three-review trigger for suspending all incremental correction is not established merely by a new finding count. The design is converging, but the claim “nothing added beyond restating an existing placement” understates the reordering and all-writer verification burden.

**Finite completion criteria before owner contract-acceptance consideration:**

1. Resolve renewal/multi-O overlap in the operative rule and proof, preferably with single-row outermost renewal transactions. Add the surviving-renewal negative schedule to the future test design.
2. Correct T-a and the overbroad row-holder/physical-lock claims. State the conditional subject-commit theorem separately from global deadlock freedom and backend disappearance.
3. Make the O-prefix precedence explicit over retained Ct-first window wording; retain Ct before shared preservation mutations. Carry the complete operation-set/revalidation obligation for keyed release, destruction and cross-operation Q settlement into the implementation mapping; no late O acquisition under Ct is admissible.

After these bounded corrections, an owner may consider architectural-contract acceptance independently of implementation authorization.
